Executive summary, v3

v2 is live, v3 is ready: Performance 28 → 71, accessibility 100

Deploying v2 put prerendered HTML, structured data, the sitemap, the social card and llms-full.txt in front of search engines and AI crawlers. v3 fixes every new finding from v2 and every partially fixed item that can be fixed in code.

  • The main-thread stall is gone. The skills cloud no longer animates off screen, and hero animations pause once the visitor scrolls past them. Style work at the top of the page fell from 8.8 s to 1.4 s per 10 s on a throttled phone; under reduced motion the page is fully idle.
  • Real hydration. React attaches to the prerendered page instead of rebuilding it: no content flash, and all 86 projects stay in the page for Googlebot.
  • 15 indexable URLs instead of 2. Three case studies and an index with Article and breadcrumb schema, and the AmelBook privacy policy in ten languages with hreflang.
  • Accessibility 100 on every page type.

What changed in v3

Performance

  • Skills cloud: runs only on screen, rests after 12 s, ~25 fps, static under reduced motion.
  • Hero animations pause off screen; the hero text no longer fades in from transparent.
  • Particle background: 30 fps, fewer particles on phones, paused in hidden tabs.
  • Leaflet map loads near the viewport; a list of countries stands in until then.
  • content-visibility on sections, with exact section jumps.
  • Vendor chunks restored; subpages on demand; 173 KB gzipped initial JavaScript.
  • WebP hero (134 → 77 KB) and avatar (8 → 2 KB).

Hydration

  • Data sections record their state during prerender; the page carries it inline or as a preloaded state.json.
  • hydrateRoot with server-rendering markers added at capture time.
  • Animated components start final and animate after mount.
  • Lists keep every item; extras render as compact hidden text.
  • No content drop and no hydration warnings on any page type.

Next opportunities

  • The skills cloud while it turns. Each rotating frame restyles about 227 elements, roughly 8 ms on a desktop CPU and 30 ms on a phone. Compositor-driven CSS 3D would make it free; that is a redesign of the component.
  • Parsing a large page. The full content in the HTML costs a 380 ms layout task at 4× CPU. Hydrating lower sections only near the viewport and loading detail dialogs on demand would cut the remaining 54 KiB of unused JavaScript and some long tasks.
  • Field data. After deploy, Search Console's Core Web Vitals report shows real-user LCP and INP, which matter more than the lab score.
